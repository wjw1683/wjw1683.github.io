Hexo 博客项目结构梳理与备份实践

偶然想起自己以前搭过一个 Hexo 博客，点开一看，网站还在线上正常访问。项目有一段时间没更新了，搁置着总觉得有些浪费，于是决定重新整理一下。

这次整理主要借助 AI 工具和 WorkBuddy 完成，包括项目结构检查、命令编写、备份执行、错误排查和结果校验。我提出了重新整理和备份的想法，参与了部分操作，查看结果并决定后续是否继续。下面记录的是这个过程和其中涉及的技术内容。

一、Hexo 项目的结构

整理的第一步不是动手改，而是先看清楚这个项目里到底有什么。以前我对它的认知比较模糊，所有文件夹混在一起看，不知道哪个重要、哪个能删。这次把它分成了几类，性质完全不同。

source/_posts/——文章源码

这是真正属于我的内容，我写的文章都在这里，一篇一个 Markdown 文件。

需要说明的是：Hexo 项目的文章通常放在 source/ 目录下，_posts 是其下的文章子目录。如果配置里改过目录名，实际路径可能不同，需要以配置文件为准。

themes/——主题模板

存放网页模板文件，决定页面长什么样。这是一套别人写好的模板，负责把文章内容渲染成网页。

关键认识：主题和文章内容是分离的，主题可以被替换。我的内容不绑定在某个主题上。理解这点之后，遇到主题层面的问题就不会太紧张。

public/——生成的静态网页

Hexo 把源码和主题处理之后，输出的静态网页文件（HTML、CSS、JS 等）就放在这里。

它不是原料，而是产物。只要源码和主题还在，通常可以重新生成，但能否顺利生成还取决于配置、依赖以及构建环境等条件。所以它不属于”随便删”的目录——在实际操作中，如果不想完整跑一遍构建流程，也可以直接查看这里已经生成的结果。

.deploy_git/——部署用的仓库缓存

这是一个隐藏目录，和 Hexo 的 Git 部署方式有关。

在这个项目里，我观察到的情况是：它内部是一个 Git 仓库，能看到完整的提交序列，检查时最新一次提交与线上仓库的最新提交相同。根据它的命名和存在形式，它应该是 Hexo 在使用 Git 部署时在本地维护的仓库，用来记录每次推送的内容。

需要说明两点：一是 .deploy_git 是使用 Git 部署方式时出现的目录，并不是所有 Hexo 项目都会有，如果用的是其他部署方式，情况会不一样；二是它保留着部署历史记录，不建议随手删除。

根目录的配置文件和依赖清单

根目录下有几个关键文件：

  • 主配置文件：定义站点标题、作者、语言、部署方式、主题选择等。主题也在这一级指定。
  • 依赖清单：记录项目依赖了哪些包、版本范围如何，以及可用的脚本命令。
  • 依赖锁定文件：把依赖的具体版本固定下来。
  • 脚手架目录：新建文章时使用的模板。

这几个是项目的”配置层”，改动它们会直接影响生成结果。

理清这几层之后，最核心的一条体会是：源码和线上网站不是一回事。线上网站只是源码经过一次加工后的产物。以前我总把它们当成同一个东西，所以既不敢动，也不知道该备份哪个。

二、检查时发现的问题

下面按”已确认”和”待确认”分开列。

已确认的问题

项目根目录没有 .git。

检查根目录时没有发现 .git 目录，也就是这个项目没有项目级的 Git 版本历史。

需要准确表述这一点：它意味着缺少一层版本管理保护，误操作或误删后无法通过 Git 回退。但这不是”源码必然丢失”——文件仍然完整存在于磁盘上，做过的备份也是完整的。只是少了一道防线。

另外，线上那个仓库里存放的是生成好的网页文件，不是源码。所以线上仓库也不能用来恢复源码。

文章没有使用分类。

项目里有一批文章，全部集中在 _posts/ 下。检查了所有文章的元信息：使用分类字段的数量是 0，使用标签字段的文章虽然有，但标签值都是空的。

也就是说，这些文章在结构上一直没有归类。

存在两份主题目录。

themes/ 下有两份主题目录：一份是 yilia，另一份的名字带”副本”字样。两份目录各自都有完整的 Git 历史（后面校验部分会列到）。

其中哪一份是实际生效的，需要以配置和构建结果确认，不能仅凭文件夹名或时间戳下结论。

配置中的若干待处理项。

检查配置时发现几处需要后续处理的地方：主题配置里的导航菜单项目很少，可用的入口有限；社交链接中有一部分指向的不是本人主页；站点 URL 配置仍是示例值；友链部分留有指向本地测试地址的占位链接。

待确认的事项

以下是我观察到但还不能确定的情况，如实列出，不做推测：

  • 两份主题目录的分工。 需要结合配置和实际生成结果才能判断哪一份在生效。
  • .deploy_git 的远程仓库地址。 检查时发现它没有配置远程地址，但它的最新提交与线上仓库一致。这是 Git 部署机制的正常表现，还是配置上有缺失——待确认。
  • 根目录的若干占位文件。 根目录下有几个大小为 0 的文件，用途不明——待确认。

三、备份过程中遇到的问题

确认项目完整之后，我决定先做备份再谈其他。主要考虑是：项目缺少版本管理，先有一份备份，后续操作会稳妥一些。

我一开始想得很简单，实际做下来发现有几个问题需要处理。

磁盘选择的判断错误

备份要选一块其他磁盘，避免和源文件放在同一块盘上。我先看了各块磁盘的剩余空间。

这一步我判断错了一次：我一度认为某块磁盘”不是真实磁盘”，把它排除了。后来核实才发现，是我把”某个工具的安装位置”和”磁盘本身”搞混了——某个工具恰好安装在那块盘上，不代表那块盘是虚拟的。

这个判断错误本身不严重，但暴露出一个问题：看系统信息时，不能只看某一处输出就下结论。

Windows junction 和符号链接

项目里有 130 个看起来像快捷方式的条目。一开始我以为都是同一种东西，仔细检查才发现是性质不同的两类：

Windows junction（目录联接）——共 125 个。检查它们的目标指向时可以看到，这些联接都指向项目内部的依赖目录。

符号链接——共 5 个。它们指向系统的 /proc/... 路径。

这两者在实现机制上有区别，但在”如何备份”这个问题上，共同的关键点是：如果不加处理，目录联接可能导致内容被展开成大量重复文件，甚至陷入递归。

最终的处理方式是使用备份工具中专门排除重解析点的选项：联接和链接本身不被复制，但它们指向的真实内容会作为普通文件正常复制过去。 那 5 个符号链接则被原样保留。

这个处理方式带来一个必须说明的结果：备份在链接结构上与原项目并不完全一致。 那 125 个联接在备份中变成了普通目录，不再以联接形式存在。这不影响文件内容，但如果想用这份备份直接还原出一个能立刻运行的开发环境，可能还需要重新安装依赖。

Git Bash 路径参数转换的问题

第一次执行备份时失败了，报错信息比较含糊。

排查后发现原因：终端会对参数做路径转换。命令中以斜杠开头的参数（如 /E 这类选项）被误识别成文件路径，改写成了形如 E:/ 的内容，导致备份工具收到错误的参数而中止。

处理方式是加一个环境变量，关闭终端的这种自动转换。

这里不贴出具体命令。因为这个问题和我使用的终端环境有关，常规的 Windows 命令行一般不会遇到，直接照搬参考价值不大。

中文目标路径的问题

解决参数问题后，又遇到了新问题：目标路径中包含中文，备份工具无法正常处理。

最终采用的方式分两步：先复制到一个纯英文名的临时路径，复制完成后再用终端把文件夹改成中文名。

中间还遇到一个小插曲：目录改名时层级结构发生了变化，需要重新调整。调整之后我重新跑了一遍校验，确认数据没有问题。

四、备份校验结果

备份完成后我没有直接认为”完成”，而是做了一组交叉验证。

186 篇 Markdown 文章的 MD5 — — 全部一致

这些校验分别能说明什么

文件数量和目录数量——文件和目录数量一致，为备份完整性提供了初步证据，但不能单独证明所有文件内容均正确。数量对得上，也可能存在内容损坏的情况。

文件实际字节总数——比数量更进一层，能确认总容量没有偏差。这里需要区分两个概念：文件内容的实际字节总数，和磁盘上占用的分配空间。同一批文件放在不同的磁盘或文件系统上，因为分配单元大小的差异，占用的物理空间可能不同。所以校验时应该比对实际字节数，而不是系统报告的”占用空间”。

186 篇文章的 MD5——MD5 是一种哈希校验方式，用于对文件内容计算一个特征值。文件内容发生变化时，MD5 通常会发生变化，但 MD5 并非无碰撞的校验方式。它的作用在于：相比单纯比对文件大小或数量，能更直接地反映内容层面的一致性。这次比对的结果是这 186 篇文章的内容一致。

需要注意它的边界：这次只对 source/_posts/ 下的 Markdown 文章做了 MD5 比对，并没有对所有文件逐一做 MD5 校验。其他文件没有逐一进行哈希比对，本次主要通过文件数量、目录数量和实际字节总数等整体统计数据进行辅助检查。

Git 提交历史——能确认仓库的提交序列和最新提交点一致，说明历史记录被完整复制。但它不能证明开发环境可用：提交历史存在，不代表依赖安装完整、不代表能直接跑起来。这次没有做恢复测试。

关于链接结构的说明

如前面所说，这次备份中：

  • 125 个 Windows junction 的目标内容被复制为普通目录，未保留联接形式；
  • 5 个指向 /proc/... 的符号链接被保留。

所以，备份在文件系统链接结构上与原项目不完全一致。它不是一个文件系统级别的完全克隆，也不能保证整个开发环境可以无差别恢复。

从”保护文章内容和源码”这个目的来说，它是有效的；但如果把它当成”随时可以还原成原样的整机快照”，这个预期是不准确的。

五、当前结论与后续

这次整理实际完成的事情有：

  • 检查了项目结构，分清了源码、主题、生成产物和部署缓存各自的角色；
  • 做了一次完整备份，并通过文件数、目录数、字节总数、文章 MD5、Git 历史等多项校验；
  • 确认了备份的内容完整性，同时明确了它在链接结构和环境还原上的边界；
  • 记录了一批已确认的问题和待确认的事项。

尚未处理或尚未确认的：

  • 两份主题目录哪一份在生效，需要结合配置和构建结果判断；
  • .deploy_git 的远程地址情况待确认；
  • 项目的版本管理还没有建立；
  • 主题中发现的几处问题还没有修改；
  • 博客的内容结构还没调整；
  • 备份没有做恢复测试。

后面准备先解决确认下来的问题，再考虑内容结构上的调整。备份已经完成，后续动手时会稳妥一些。

就这样，先记录到这里。
